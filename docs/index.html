Stage 1

Diagnosis & Baseline Bottlenecks

Analyzing unoptimised schema behavior using EXPLAIN (ANALYZE, BUFFERS) to uncover unbounded correlated subqueries, missing foreign key indexes, and CPU-intensive expression mismatches.

⏱ Latency: 4,216 ms
💾 Shared Reads: 5.29 GB
🔍 Plan: Seq Scan

Root Cause Findings

  • Unbounded Correlated Subqueries: Running customer lifetime spend forced PostgreSQL to execute two full sequential scans across all 1.2M rows for every single matching customer row.
  • Missing Foreign Key Indexes: Relational joins between customers.id and orders.customer_id degrade to a Parallel Seq Scan scanning 30,000 disk blocks (~240 MB).
  • Expression Mismatches: Evaluating WHERE UPPER(c.email) = 'USER2500@EXAMPLE.COM' prevented standard index lookups, forcing row-by-row function evaluation.
sql/02_diagnose.sql — Correlated Anti-Pattern 
EXPLAIN (ANALYZE, BUFFERS)
SELECT 
    c.id AS customer_id,
    c.name,
    c.email,
    (SELECT MAX(o.order_date) FROM orders o WHERE o.customer_id = c.id) AS latest_order_date,
    (SELECT SUM(o.order_total) FROM orders o WHERE o.customer_id = c.id) AS lifetime_spend
FROM customers c
WHERE c.email LIKE '%user49%';

Stage 2

Production Index Engineering

Deploying targeted index structures: standard B-Trees, Functional expression indexes, GIN for semi-structured JSONB payloads, Partial indexes for status filtering, Covering indexes for zero heap fetches, and lightweight BRIN for time series.

⚡ Point Lookup: 1.65 ms
🚀 Covering Scan: 0.134 ms
📦 Heap Fetches: 0

Covering Index Mechanics (INCLUDE)

By defining orders (customer_id, order_date) INCLUDE (order_total, order_status), non-key payload columns are stored directly in the index leaf pages. PostgreSQL satisfies the query entirely from the B-tree leaf nodes without touching the underlying heap table pages.

sql/03_add_indexes.sql — Covering B-Tree 
CREATE INDEX IF NOT EXISTS idx_orders_customer_covering 
    ON orders (customer_id, order_date) 
    INCLUDE (order_total, order_status);

-- Functional index for instant LOWER() case-insensitive matches
CREATE INDEX IF NOT EXISTS idx_customers_email_lower 
    ON customers (LOWER(email));

Stage 3

Query Plan Rewriting & LATERAL Joins

Eliminating correlated subqueries completely by rewriting into a LEFT JOIN LATERAL combined with the covering index, dropping execution time from 4,200 ms to 0.168 ms.

⚡ Latency: 0.168 ms
🚀 Speedup: >24,000x
💾 Buffer Reads: 9 blocks

Before vs After Query Transformation

sql/04_rewrite_queries.sql — LEFT JOIN LATERAL 
SELECT 
    c.id AS customer_id,
    c.name,
    c.email,
    agg.latest_order_date,
    agg.lifetime_spend
FROM customers c
LEFT JOIN LATERAL (
    SELECT 
        MAX(o.order_date) AS latest_order_date,
        SUM(o.order_total) AS lifetime_spend
    FROM orders o
    WHERE o.customer_id = c.id
) agg ON true
WHERE LOWER(c.email) = LOWER('user2500@example.com');

Stage 4

Denormalization via Materialized Views

Pre-aggregating analytical dashboard KPIs across all 5,000 customers. Enables sub-millisecond lookups with non-blocking concurrent refresh.

⚡ Latency: 0.039 ms
🚀 Speedup: 4,050x
🔄 Concurrent Refresh

Materialized View Definition

sql/04_rewrite_queries.sql — mv_order_summary 
CREATE MATERIALIZED VIEW mv_order_summary AS
SELECT 
    customer_id,
    COUNT(*)                   AS total_orders,
    SUM(order_total)           AS total_spent,
    ROUND(AVG(order_total), 2) AS avg_order_value,
    MAX(order_date)            AS last_order_date
FROM orders
GROUP BY customer_id
WITH DATA;

-- UNIQUE index enables non-blocking background refreshes
CREATE UNIQUE INDEX idx_mv_order_summary_customer_id 
    ON mv_order_summary (customer_id);

-- Operational refresh command:
-- REFRESH MATERIALIZED VIEW CONCURRENTLY mv_order_summary;

Production Architectural Trade-offs

✓ Advantages

  • Sub-millisecond reads (0.039 ms).
  • Zero CPU or lock contention on active orders table.
  • Refreshes occur concurrently in background without blocking reads.

⚠ Trade-offs

  • Eventual consistency between scheduled refresh intervals.
  • Additional WAL generation during concurrent rebuild.
Stage 5

Declarative Yearly Range Partitioning

Restructuring monolithic 1.2M-row storage into declarative annual partitions (orders_2020 through orders_2024 plus default). Query planner prunes untouched years before execution.

✂️ Pruning: 80% I/O Cut
💾 Blocks: 6,329 vs 30,000
📅 5 Annual Partitions

Partition DDL & Primary Key Rules

In PostgreSQL declarative partitioning, composite primary keys must include the partitioning column: PRIMARY KEY (id, order_date).

sql/05_partition_orders.sql — Range Partitioning 
CREATE TABLE orders_partitioned (
    id BIGINT NOT NULL,
    customer_id INT NOT NULL,
    order_date TIMESTAMP NOT NULL,
    order_total NUMERIC(10, 2) NOT NULL,
    order_status VARCHAR(20) NOT NULL,
    PRIMARY KEY (id, order_date)
) PARTITION BY RANGE (order_date);

CREATE TABLE orders_2023 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

Stage 6

Transaction Pooling with PgBouncer

Mitigating process-forking overhead and context switching under high client concurrency using PgBouncer in transaction mode on port 6432.

🚀 Throughput: 625.75 TPS
⚡ Speedup: 32x TPS
🔒 Fixed 20 Server Workers

Why Transaction Pooling Matters

PostgreSQL allocates a dedicated Linux backend process (~5-10 MB RAM) per client. Under 100+ concurrent connections, process contention cripples performance. PgBouncer allows 1,000 client sockets to share 20 server workers.

docker-compose.yml — PgBouncer Configuration 
pgbouncer:
  image: edoburu/pgbouncer:latest
  environment:
    POOL_MODE: transaction
    MAX_CLIENT_CONN: "1000"
    DEFAULT_POOL_SIZE: "20"
    LISTEN_PORT: "6432"
  ports:
    - "6432:6432"

Size: 24 kB • 1,000x smaller!

Leverages physical block order for sequential append tables. Maps min/max timestamps per block range; consumes only 24 kB compared to a 26 MB B-tree.
idx_customers_email_lower Functional B-Tree
Size: 216 kB
customers (LOWER(email))
Stores precomputed lowercase hashes for zero-overhead case-insensitive lookups, preventing sequential scans from functions like LOWER().
idx_orders_details_gin GIN Inverted
Size: 125 MB
orders USING GIN (order_details)
Maps individual keys and nested attributes inside semi-structured JSONB payloads for lightning-fast JSON containment operators (@>).
idx_orders_completed_date Partial B-Tree
Size: 18 MB • Saves 30% Space
orders (order_date) WHERE order_status = 'completed'
Only indexes completed order rows (70% of dataset). Excludes pending/cancelled rows to save RAM and keep the index resident in memory cache.

Telemetry & Monitoring

Production Observability with pg_stat_statements

In high-volume production, slow queries must be caught proactively without running continuous manual EXPLAIN calls.

Top 10 Slowest Queries by Total Cumulative Time 
SELECT 
    calls,
    ROUND(total_exec_time::numeric, 2) AS total_time_ms,
    ROUND(mean_exec_time::numeric, 2)  AS mean_time_ms,
    ROUND((100.0 * total_exec_time / SUM(total_exec_time) OVER())::numeric, 2) AS pct_load,
    rows,
    SUBSTRING(query, 1, 80) AS query_preview
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
Buffer-Heavy Queries & Cache-Hit Ratio Monitor (<95% Alert) 
SELECT 
    query,
    calls,
    shared_blks_hit,
    shared_blks_read,
    ROUND((100.0 * shared_blks_hit / NULLIF(shared_blks_hit + shared_blks_read, 0))::numeric, 2) AS cache_hit_ratio
FROM pg_stat_statements
WHERE calls > 5
ORDER BY shared_blks_read DESC
LIMIT 5;
